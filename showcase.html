The problem

Two people, one seat, the same millisecond

The naive approach — read whether the seat is free, then mark it taken — has a fatal race: two requests can both read free before either writes taken. Both succeed. The seat is sold twice.

The fix isn't a bigger lock or a more careful check. It's moving the guarantee to where concurrency can't reach around it: a database constraint.

The model — hard-hold · create-on-pay

A seat's life in three steps

Holds are exclusive, tickets exist only once sold, and abandoned holds free themselves.

01 · HOLD

Exclusive, time-boxed

Selecting seats creates an Order + one PENDING reserve per seat, with a 5-minute TTL. While you hold A10, no one else can hold or buy it.

02 · PAY

All-or-nothing

Payment creates the SOLD tickets, confirms the reserves and decrements stock in one transaction. If any seat fails, the whole order rolls back.

03 · EXPIRE

Self-healing

A background sweeper cancels stale holds. Because the hold index is partial, cancelling a hold frees the seat automatically — no cleanup needed.

How correctness actually works

The check can lie. The constraint can't.

Application pre-checks exist only for a nice UX message. The real guard is the constrained INSERT.

✕ App-level check — races
// two requests, same instant
if (seatIsFree(A10)) {   // both read: free
  markTaken(A10);          // both write: taken
}                          // → sold twice

There's a gap between the check and the act. Concurrency lives in that gap.

✓ Unique index — race-proof
-- partial UNIQUE (concertId, seatNumber)
--        WHERE status = 'pending'
INSERT INTO reserve (…);   // 1st: ok
INSERT INTO reserve (…);   // 2nd: UNIQUE fails
// → caught → 409 { seatNumbers, reason }

The database rejects the second write outright. There's no gap to race through.

Why no pessimistic locks? SQLite has no row-level locking — so instead of SELECT … FOR UPDATE, exclusivity rides on unique constraints + conditional writes, which are race-proof on any engine. The code documents exactly where a row lock would go on Postgres — a deliberate, portable choice, not an accident.

Architecture

Layered, injected, testable by construction

Each layer knows only the interface below it. Nothing news-up its own dependencies — which is exactly why the whole thing is testable.

RouteRoute factory + validate(zod DTO) — per-endpoint input validation
ControllerThrows domain errors; a central 4-arg middleware maps them to HTTP. No try/catch.
ServiceBusiness logic + transactions (createQueryRunner, all-or-nothing)
RepositoryManager-aware — methods optionally join the caller's transaction
TypeORM→ SQLite · unique & partial-unique indexes enforce the invariants
EventBusAfter commit → in-process bus → socket.io bridge → per-concert WebSocket room

"What did you do on this project?"

The short version, in credits

The takeaway: how to choose the right concurrency primitive for the platform — DB constraint vs. lock vs. transaction — how to structure a codebase so it's testable by construction, and how to make deliberate, documented trade-offs rather than accidental ones.
